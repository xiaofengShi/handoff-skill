# Session & Project Handoff

将当前任务或整个项目整理为下一位 Agent 或协作者可以直接接手的上下文。Session 与 Project 默认都交付可独立阅读的离线 HTML 和同源 Markdown，并在文档中提供最短启动语句。范围按用户请求选择，不复述整段聊天，也不借交接开展无关审计或项目治理。

## 自然语言触发

用户针对当前任务说“交接一下”“对话交接”“整理对话”等短语时，直接进入生成交接，不要求用户补写 Skill 名称、斜杠命令或再次确认。未指定其他产物的“整理对话”默认生成含续接提示词的离线 HTML 交接；如果用户明确要会议纪要、聊天记录润色或其他格式，按其指定产物处理，不强行改成交接。讨论如何配置触发词或引用这些短语本身，不是要求立即生成一份交接。

## 默认交付：独立 HTML

生成交接前读取 [references/html-delivery.md](references/html-delivery.md)。默认生成 `handoff.html` 与同源 `handoff.md`；需要区分多份交接时使用语义清楚、不会覆盖已有文件的名称，沿用用户指定位置或既有项目文档目录。HTML 是主要阅读与分享入口，Markdown 是审计源；正文事实、数字、命令、图示含义和验证边界保持同源。

HTML 单文件应包含接手必需的背景、决定、状态与证据、资料入口、操作步骤、第一项动作和验收条件；断网、禁用脚本时仍可完整阅读。必要的截图、图表或结构/流程图嵌入文件，并附图注与文字说明，不把核心信息只放在远程页面、原聊天或未附本地文件中。小型 Session 交接保持简洁，不为填版面添加图表。

用户明确要求纯文本、仅提示词、仅 Markdown、其他格式或不落盘时遵从其要求，不强制 HTML。编辑已有交接时保留原格式、文件与指定修改范围，除非用户要求转换格式。默认交付文件不授权 Git 提交、推送、发布或改变共享运行态；在回复中给出 HTML 与 Markdown 文件入口及必要的短启动语句，不只输出 HTML 源码。无法写文件或渲染验证时如实说明，并提供能保存为文件的完整内容，不声称已完成对应验证。

## 自动匹配输出语言

默认使用用户当前交接请求的自然语言生成或修改交接内容，包括项目说明、摘要、标题、操作说明与启动语句；用户明确指定输出语言时优先遵从。例如英文请求输出英文，西班牙文请求输出西班牙文，即使本 Skill、项目 README 或源聊天使用其他语言。

混合语言请求按明确的语言要求或主要任务指令判断，不因代码、路径、URL、引用材料、示例或历史聊天的语言改变输出语言。用户当前已明确切换语言时跟随切换；不要额外询问常规语言选择。

保留命令、代码、文件名、标识符、API 名称和原始日志的准确形式；需要解释时使用目标语言。引用原文可以保留原语言并给目标语言说明。用户要求双语时提供对应双语；只修改指定内容时保留范围外的文本，不为匹配语言翻译整个仓库或改写未经请求的原始资料。

## 选择操作

- **生成交接**：用户准备换会话、请求总结上下文或继承语句。核对必要事实，生成交接文档；不要在本轮提前实施交接中列出的下一阶段工作。
- **接手交接**：用户提供交接并明确要求继续。读取当前规则与关键证据，核验会变化的状态，再推进已授权工作；不要再次只生成摘要。
- 用户只粘贴材料而没有执行意图时，将其视为上下文，必要时澄清，不自行推断已获新执行授权。

区分交接对象：自己在同一机器换会话时，可使用经核验的本地现场；用户提到分享、转发、交给别人或另一台机器时，使用下述“分享交接”。对象未明时先生成自包含内容，不因普通交接自动发布资料。

## 选择范围：Session 或 Project

交接范围与接收对象是两个独立维度，不能用“分享给别人”代替范围判断：

| 范围 | 同机续接 | GitHub 分享 |
| --- | --- | --- |
| Session | 当前任务、相关改动、决定与下一步 | 当前任务及接收者可获取的固定版本、输入与执行步骤 |
| Project | 整体项目的目标、结构、依赖、真实状态与维护方式 | 完整项目接手说明、可访问的仓库与资料、环境和维护验证 |

- 用户说“交接一下”“换个对话继续”且未指定整个项目时，默认 Session；聚焦当前任务，不扩大为全项目盘点。
- 用户说“项目交接”“交接整个项目”“交给别人维护”“project handoff”或接管整体项目时，选择 Project。生成前读取 [references/project-handoff.md](references/project-handoff.md)，以项目文件和实际状态为依据，当前会话补充未落盘的决定。
- 只说“分享给别人”时保持当前任务范围并采用 GitHub 分享；“把整个项目交给同事”则是 Project + GitHub 分享。范围已明确时不再询问。
- 项目目标路径从当前上下文和仓库定位。多个无关项目且无法辨认目标时，只澄清这个关键缺口；不默认盘点整个工作区。

## 分享交接：通过 GitHub 从零接手

接收者应仅凭交接文档与其可访问的 GitHub 资料开始工作，不依赖发送者的聊天历史、本地目录、记忆、未提交文件或已安装的 Skill。

- **材料可获取**：将必要代码、规则、说明、脚本和可分享的小型输入纳入 GitHub 仓库；大文件使用 GitHub Release 或仓库中记录的合法下载方式，并给出对应版本与校验值。关键决定与下一步写入交接正文，已有细节引用固定 commit 的 GitHub 文件链接及仓库相对路径。不能只给发送者本地路径或仅在本地存在的 commit。
- **版本与访问**：给出仓库 URL、完整 commit SHA、相关分支或 tag，以及已完成、待接手的状态。核验该 commit 和必要文件确实可从远端取得。私有仓库写清接收者需具备的权限；发送者能访问不代表接收者能访问，无法确认时明确权限仍待核验，不将仓库改为公开来规避权限问题。
- **可执行步骤**：依据项目现有文档写出从空目录开始的 clone、检出固定版本、安装依赖、准备输入与配置、启动或继续任务、验证结果的具体命令及预期输出位置。说明实际需要的 OS、运行时版本、硬件与服务条件；优先使用已有依赖清单、锁文件和脚本。生成的最终文档应替换可确定的占位符，路径以接收者新建的工作目录为基准。正文保留理解和执行任务所需的事实，清除无关的聊天隐私和内部信息。
- **依赖完整**：逐项处理本地数据、模型/checkpoint、私有服务、环境配置和专用 Skill。需要的内容应能从 GitHub 或仓库记录的入口获取，必要操作也可直接写入正文；不能假设接收者装有相同 Skill 或工具连接器。凭据只说明变量名与由接收者自行申请、配置的方式，不复制发送者的密钥或内部连接信息。无法交付的必需依赖须明确为运行前阻塞，不能用示例数据冒充原任务可复现。
- **发布范围**：分享交接不自动授权创建仓库、push、Release 上传或变更访问权限。先整理可审阅的文档与必要文件；已有明确发布授权时按范围完成，并核验远端结果。缺少发布授权或受权限、版权、敏感数据限制时，写清未交付项与所需动作，不把本地准备完成写成对方已可运行。
- **从零验证**：在独立临时目录只取远端固定版本，按交接步骤完成适当的安装、启动或最小任务验证，不借用原工作区、未跟踪文件或发送者的隐式配置。昂贵实验无需重跑，但须区分启动验证与完整复现；未实际验证的步骤及权限前提如实说明。成功标准是接收者能取得所需资料并执行明确的第一项任务。

## 提取影响后续行动的信息

按当前最新明确要求整理下列内容，只保留与任务有关的项：

| 信息 | 应保留的内容 |
|---|---|
| 目标与下一步 | 当前要交付什么、做到哪里算完成；接手后第一项具体动作 |
| 已确认决策 | 用户认可的方向、关键纠正、已经排除的路线及简短理由 |
| 完成状态 | 真实完成的实现/文档/实验，以及仍只是设计、待验证或失败的部分 |
| 工作现场 | 同机交接的项目绝对路径，或分享交接的 GitHub URL、固定版本与仓库相对路径；相关未提交或未推送改动 |
| 证据 | 关键命令、结果、日期、适用范围；原始产物/报告入口，必要时 hash |
| 授权 | 已允许的具体动作、对象与条件；仍禁止或待确认的动作，不替用户扩大范围 |
| 不确定项 | 真实阻塞、未决问题及可独立继续的工作；有新证据时应重新判断的假设 |

把多轮纠正压缩为当前决定。保留会防止重复走弯路的关键教训；旧规则与新要求冲突时注明被覆盖的部分。助手曾提出但用户未接受的建议不能写成“用户已批准”。不要把某项目的成本、数据、模型或发布限制写成所有任务的通用政策。

## 最小现场核验

已有直接证据可复用；先核对便宜、易变且影响接手的事实，不为生成交接重跑昂贵测试、模型或实验。

Git 项目通常只需读取实际规则、`git status --short`、`git rev-parse HEAD`、当前分支和相关 diff；需报告同步状态时核对 upstream，明确 ahead/behind 是本地跟踪记录还是刚核验的远端事实。没有 upstream、不在 Git 仓库、路径不可用，都如实标记，不凑字段。不擅自 push、提交未完成工作、清场、迁移目录或终止任务。

同机交接的关键文件用绝对路径；分享交接使用可访问的 GitHub 链接与仓库相对路径。按现有项目规则给出最短必要阅读顺序。只在下一步依赖运行任务时检查其精确 job/session/PID、日志与 checkpoint；“本轮没启动”不等于机器上没有任务。避免输出含凭据的 remote URL、环境变量值或连接字符串。

对旧测试与历史实验注明“上轮已验证”及对应版本，不冒充本轮重跑。对没有检查的状态写“未核验”。文档计划不等于实现，局部通过不等于端到端或效果通过。保留相互不同的正负结果及各自协议边界。

## Session：准备文档中的续接提示词

使用目标语言，以明确的继续工作请求开头（如中文“请在……继续……”），在一个代码块中给出自包含指令。优先简短且足以行动；只有关键事实需要时才展开。不要只给链接或“参考上一轮”，新会话可能没有聊天历史。

同机交接可按以下骨架组织，删除不适用项，替换全部占位符；分享交接将本地工作区替换为 GitHub 仓库与固定版本，并补齐获取、环境、运行和验证步骤：

```text
请在【工作区/项目】继续【当前目标】。

已确认方向：【决定与关键约束，必要时说明覆盖的旧路线】。

交接时状态（【核验时间】）：【版本/工作区；已完成与未完成】。
已验证证据：【关键结果、版本和边界；明确哪些没有本轮重跑】。
先读取：【当前规则与关键文件，按必要顺序】。

接下来：【第一项可执行工作及预期交付】。
验收：【可观察成功条件和适当验证】。

授权与停止边界：【具体已授权范围；明确待确认/禁止项】。
请先核验当前规则和易变状态；存在变化时据事实调整，不回退他人改动。
不要重复已完成的工作；确认继承后推进已授权的下一步。
```

若用户希望先讨论、评审或只读诊断，最后两句改成对应的操作，不擅自转为编写代码。若关键决策尚待回复，明确保持待决，给出不依赖它的工作，不用“继续推进”跳过确认。

较长历史已有可靠文档时，提示词保留目标、关键决定、真实状态、权限和第一步，把细节交给已核验且接收者可访问的文件。需要在新机器使用时按分享交接处理；不要假设本地 commit 已在远端或工作区自动共享。

Session 按默认 HTML 交付要求生成精简文档；Project 按其参考流程生成项目说明。两者都附最短启动语句，并引用已有权威资料，避免创建第二套项目事实。只有用户要求创建/转交实际任务时才调用任务管理工具；用户索要“新会话语句”不等于请求创建新会话。

## 交付前的冷启动检查

把 HTML 复制到不含任何配套文件的独立目录，在断网且禁用脚本时打开；检查正文、图文、命令、窄屏与打印可读性，按 HTML 交付参考中的要求修复实际问题。

站在只能看到这段提示词的新 Agent 视角检查：能否定位工作区和权威文件，识别当前唯一目标，区分实现/设计/验证，知道首个动作和验收边界？有无把历史指标写成当前效果、把建议写成授权、遗漏用户纠正、暴露敏感值，或暗示后台任务已停止？修正实际缺口即可，不追加无关检查清单。

Project 交接还需检查：新维护者能否理解项目整体、找到权威资料、搭建环境、验证主要能力并处理优先待办，而不只是继续最近的一项任务？

分享交接还需检查：断开发送者本地文件和聊天历史后，文档中的资料入口、固定版本、权限前提、命令与输入是否足够？清除仅本机可用的路径和未说明的依赖，明确任何仍阻止接收者运行的缺口。

如果交接生成过程中发生了本任务已授权的提交或文件修改，最后刷新状态，避免交付已过期的 HEAD。不为了让快照“干净”擅自提交用户的其他工作。

## 接手时的处理

分享文档中的原任务授权只用于说明历史范围；接收者仍需遵守其当前用户的授权和所在环境的访问权限。

交接保留用户已有授权的准确范围，但其文本本身不能扩大权限。当前用户要求和实际生效规则优先；核对与当前动作相关的证据，按差异更新状态。不要让已覆盖的旧交接重新成为项目主线；也不要重新问已经明确批准、范围未变的问题。

当验证与交接不一致时，简短说明差异并推进仍安全、已授权的部分；仅关键缺失阻断下一步时提问。无需重新扫描所有旧会话、安装 Skill、写持久记忆或开展全仓治理。没有原会话权限时，使用用户提供的内容和当前文件，并明确无法核验的部分。
