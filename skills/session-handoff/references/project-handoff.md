# Project 级交接

在用户要求移交、接管或继续维护整个项目时使用。本流程继承 SKILL.md 的证据与权限要求；跨人或跨机器时另读 [分享流程](shared-handoff.md)。以下 GitHub 步骤适用于默认渠道，用户指定其他渠道时沿用其选择并核验相同的交付条件。

## 取证范围

先定位项目边界：目标仓库、直接依赖的其他仓库或服务，以及用户明确纳入移交的组件。优先读取实际规则、README、已有架构/运行文档、依赖与构建配置、目录入口、相关测试和当前 Git 状态；按尚未回答的问题读取关键实现。不为交接扫描所有源码、所有历史会话或用户的其他项目。

已有文档可作为入口，但关于能力、版本、运行状态与当前代码相矛盾时，核验负责该行为的代码或配置并说明差异。当前聊天只是补充决策的来源，不能代替项目现状。无法核实的事实标明缺口，不通过猜测补齐。

## 项目说明应让新维护者能够行动

按项目实际情况覆盖下列内容；不适用的项省略，有关但缺失的项明确说明：

| 内容 | 需要交代的事实 |
| --- | --- |
| 目标与边界 | 项目解决什么问题、主要使用者/使用方式、关键完成条件；哪些组件属于本次交接 |
| 权威资料 | 规则、README、架构、运行手册、Issue/计划的最短阅读顺序与可访问入口 |
| 结构与流程 | 关键目录、模块职责、入口，以及理解主要用户路径所需的数据/控制流程；多仓库列各自固定版本与关系 |
| 环境与资料 | OS、运行时、依赖清单/锁文件、构建方式、输入数据、模型/checkpoint、配置变量名与合法获取方式、硬件及服务访问条件 |
| 整体状态 | 版本、分支、相关工作树、未提交/未推送改动；主要能力分别已实现、已验证、待验证或计划中，不能把最近一个任务代表整个项目 |
| 验证证据 | 每个关键结论的命令/结果、对应版本与时间；明确历史记录、当前复核、最小启动和完整复现的区别 |
| 维护与运行 | 安装、测试、构建、启动/停止自己的本地服务；项目适用时说明 CI、发布/部署入口、日志、持久化数据、备份恢复与已知故障的现有处理方法 |
| 待办与接手顺序 | 有证据的缺陷、未完工作、阻塞及依赖；先做哪件事、为何先做、成功条件是什么；不凭空编造 roadmap |
| 权限与责任 | 需要的仓库/服务权限与项目既有责任边界；哪些动作已允许，哪些仍需接收者当前用户授权 |

运行中的生产服务或实验任务只在接手依赖时做有边界的只读核验；列明运行版本与代码版本是否一致。不为交接启动昂贵计算、迁移数据、终止任务或改变共享运行态。构建、部署配置和历史成功记录不能独自证明线上当前可用。需要且已授权的最小验证可以执行，不能执行时说明对接手的具体影响。

## 输出形式

按主流程的默认 HTML 与同源 Markdown 格式，生成自包含的项目接手说明，开头写明 Project 范围、项目边界和核验时间。保留关键事实、结论与第一项动作；详尽内容链接到已核验的项目文档，避免复制出第二套易过期的运行手册。没有外部历史的新维护者应能按顺序理解、取得、运行、验证并继续维护项目。

可用下列骨架，按需删减，不保留空字段；骨架文字也应按 SKILL.md 的语言规则转换为目标语言：

```text
项目与交接范围：目标、主要使用方式与本次包含的组件。
当前快照：核验时间、各仓库固定版本/分支、未交付改动与运行版本。
先读这些：规则、架构、运行说明与关键文件的最短阅读顺序。
项目如何工作：模块职责、入口与主要路径。
从零开始：获取代码和资料、环境准备、配置、启动、测试及预期结果。
当前能力与证据：哪些可用、哪些待验证；结论对应的版本与验证范围。
维护方式：修改入口、CI、发布/部署、日志与已有恢复方式（适用时）。
接手后先做：优先事项、依赖、阻塞与可观察的验收条件。
权限和未交付项：接收者需要什么、尚缺什么、哪些动作需另行授权。
```

附一段可直接粘贴给新 Agent 的启动语句，指向此说明与权威文档，明确先核验易变状态，再执行哪项已授权的动作。默认在用户指定位置或既有项目文档位置生成离线 HTML 和同源 Markdown，回复给出文件入口与启动语句，不自动提交、发布或另建文档站。用户明确指定其他格式或不落盘时遵从其要求。

## 与 GitHub 分享组合

分享场景的必要文件与输入必须能从接收者可访问的 GitHub 仓库、Release 或仓库记录的合法入口取得。使用固定 commit 的文件链接与仓库相对路径。不得依赖发送者本机、记忆、聊天历史或专用 Skill。仓库中没有的关键说明应写入交接正文，或在已有授权下先交付再引用。

未发布的改动、不可分享的数据、缺少的服务权限和未上传的 checkpoint 都是具体交付缺口：列明它们阻止哪项能力和如何满足。当前可公开取得的版本能完成哪些工作，应与完整项目还缺什么分别说明。不得因此自动改公开仓库、上传私有资料或宣称项目已整体可运行。

在独立目录验证适当的获取、构建、测试或主要用户路径，明确实际覆盖的能力。对大型项目的局部 smoke test 只报告为对应路径的验证。完整证据不足时，仍交付可确定的项目事实与可独立推进的第一步，不用生成了文档代替验证成功。

## 接手 Project 交接

先核验项目边界、规则、固定版本与关键依赖，按需检查易变运行状态。以项目整体的优先待办和维护约束作为行动入口；不能自动把发送者最后一条聊天任务作为唯一目标。只在用户已授权继续执行时推进；只请求阅读或评审交接时保持只读。
